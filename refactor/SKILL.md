# PL/SQL refactor — byte-safe workflow

Prefer deterministic evidence to broad text replacements. All four tools are available. It accepts JSON specs and report formats; no Oracle connection or Git checkout is required. Always keep the original backup and review package-level API/visibility changes separately.

1. **Inventory and probe, do not edit.** Run `plsql-parse refactor findrepeats scan OLD.sql --range A:B --min-len 4` for repeated families. The default `both` mode includes whitespace-exact and literal-parameterized (`skeleton`) families and ignores commented-out SQL. For each candidate, run `plsql-parser findrepeats unique OLD.sql A B`; whole-file duplicate matches make content-addressed replacement unsafe. Inspect its line references and variable lines manually before choosing an extraction.
2. **Design helper contracts.** Extract only behavior-equivalent sequences. Determine parameter types from declarations, ensure names are unused, and preserve exception scope, SQL side effects, transaction semantics and visibility. Local nested subprograms cannot automatically be called from a package-level helper. Do not merge merely similar divergent control flow.
3. **Create a splice spec.** Address edits by original **1-based line numbers** (`insert` after A, `replace`/`delete` A..B). Prefer `{"extract":[start,end]}` entries referencing `file_ref` for every existing line, never retype identifiers or string literals. Run `plsql-parser refactor splice spec-from-diff changes.diff NEW.sql changes.json` for an audited known before/after normal-format diff; generated hunks include old-side audit lines. See [spec-format.md](refactor/references/spec-format.md).
4. **Dry run and verify.** Run `plsql-parser refactor splice patch changes.json OLD.sql CANDIDATE.sql`; compare `cmp -s CANDIDATE.sql NEW.sql` or invoke `plsql-parser refactor splice verify changes.json CANDIDATE.sql`. `patch` never modifies OLD. Inspect normal diff and hash/line counts; ensure LF-only, one trailing `\n` after EXIT, and unchanged out-of-scope sites.
5. **Structural balance on BOTH versions.** Run `plsql-parser refactor balance --expected-residual 2 --delta OLD.sql CANDIDATE.sql`.  Confirm IF/ENDIF, LOOP/ENDLOOP, CASE expression counts, and an unchanged residual (package-level `END`s). Token accounting is not a PL/SQL compiler.
6. **Acceptance checks.** Run `plsql-parser refactor checklist checks.json --json checks-result.json`. Check md5, LF line count, critical token/label counts, file suffix and no-CR bytes. Checklist path references resolve relative to its JSON file; `cmd` checks execute trusted shell commands (avoid untrusted JSON). On any failed assertion stop; do not claim verification.
7. **Apply only after review.** Run `plsql-parser refactor splice apply changes.json TARGET.sql` only if TARGET is still the intended pristine input. It writes `TARGET.sql.pre-apply.bak`, validates preconditions, builds the candidate, validates postconditions, atomically replaces TARGET, re-checks, and restores from the backup on any exception. Never apply a spec without an audited precondition (md5 and line count) and postconditions.
